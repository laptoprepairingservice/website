# Supabase Database Migration Rules

## Purpose

These rules define how the AI must handle database changes made to the project's Supabase database, especially when using the Supabase MCP server.

## 1. Always Record Database Changes

Whenever you create, alter, delete, or otherwise modify anything in Supabase through MCP, you MUST create or update a migration record in the repository.

This applies to:

- Creating tables
- Altering tables
- Dropping tables
- Adding or removing columns
- Changing column types
- Adding or changing constraints
- Creating indexes
- Creating functions
- Creating triggers
- Creating RLS policies
- Altering RLS policies
- Creating enums/types
- Changing database permissions
- Other persistent database/schema changes

## 2. Migration Files Are the Source of Truth

Never rely only on changes made directly through the Supabase MCP server.

Every persistent database change must have a corresponding SQL migration file committed to the repository.

Use the project's existing migration directory if one exists.

Preferred structure:

```text
supabase/
└── migrations/
    ├── name_of_file.sql
    └── 20260912000300_add_product_indexes.sql
```

Use a unique, chronological migration name.

## 3. MCP Changes Must Be Reproducible

If a database change is performed through the Supabase MCP server:

1. Perform the requested database change.
2. Obtain or reconstruct the exact SQL required to reproduce that change.
3. Create a corresponding migration file.
4. Add the SQL to the migration file.
5. Verify that the migration represents the actual database state.
6. Keep the migration file in the repository for future deployments.

The migration file must allow another developer or a fresh Supabase project to reproduce the same database change without relying on the previous MCP operation.

## 4. Never Make Unrecorded Schema Changes

DO NOT make a persistent Supabase schema change through MCP and leave it undocumented.

Bad:

```text
AI → Supabase MCP → CREATE TABLE products
```

without creating a migration file.

Good:

```text
AI
  ↓
Supabase MCP
  ↓
Create/modify database
  ↓
Create migration SQL file
  ↓
Verify migration
  ↓
Commit both code and migration
```

## 5. Preserve Existing Migrations

Never modify an old migration simply to make the current database state correct.

If a change is required after an existing migration has already been created, create a NEW migration.

For example:

```text
20260912000100_create_products.sql
20260912000200_add_product_sku.sql
20260912000300_add_product_indexes.sql
```

Do not rewrite:

```text
20260912000100_create_products.sql
```

after it has already been applied.

## 6. Migration SQL Must Be Explicit

Prefer explicit SQL over undocumented MCP operations.

Example:

```sql
create table public.products (
    id bigint generated by default as identity primary key,
    name text not null,
    sku text not null unique,
    created_at timestamptz not null default now(),
    updated_at timestamptz not null default now()
);
```

Do not create a migration containing only comments such as:

```sql
-- Created products table using Supabase MCP
```

The actual SQL required to reproduce the change must be present.

## 7. Record Important Database Decisions

When a migration involves a significant architectural decision, add a short comment explaining WHY the change was made.

Example:

```sql
-- SKU is unique because it is used as the stable product identifier
-- across inventory and order records.

create unique index products_sku_idx
on public.products (sku);
```

Do not add unnecessary comments for obvious SQL.

## 8. Verify After Migration

After applying a migration through MCP, verify the resulting database state.

Check where appropriate:

- Table exists
- Columns exist with correct types
- Primary keys
- Foreign keys
- Unique constraints
- Indexes
- Functions
- Triggers
- RLS status
- RLS policies
- Defaults
- Nullable/non-nullable fields

If the actual database state differs from the migration file, fix the migration record before considering the task complete.

## 9. Deployment Requirement

A database change is NOT considered complete until both are present:

1. The change exists in Supabase.
2. The SQL migration exists in the repository.

The repository must contain everything necessary to recreate the database in a new environment.

## 10. Before Creating a New Migration

Before making a database change:

1. Inspect the existing schema.
2. Inspect existing migrations.
3. Determine whether the requested functionality already exists.
4. Avoid creating duplicate tables, indexes, functions, triggers, or policies.
5. Follow the project's existing naming conventions.

## 11. Destructive Changes

For destructive operations such as:

```sql
drop table
drop column
drop function
```

or potentially destructive data changes:

- Clearly identify the destructive operation.
- Verify that it is actually required.
- Prefer a safe migration strategy when possible.
- Never silently delete production data.

If the operation could cause data loss, explicitly warn before executing it unless the user has already clearly authorized that exact destructive operation.

## 12. Migration Documentation

If the project contains a database documentation file, update it when a migration changes an important part of the schema.

For example:

```text
docs/
├── database/
│   ├── schema.md
│   └── migrations.md
```

The migration SQL remains the authoritative deployment record.

Documentation should explain the database design; migration files should contain the executable history.

## 13. Final Response After a Database Change

After completing a Supabase database change, report:

- What was changed
- Which migration file was created
- Whether the database change was verified
- Any important deployment notes

Example:

```text
Supabase migration completed.

Migration:
supabase/migrations/20260912000300_add_product_indexes.sql

Changes:
- Added index on products.category_id
- Added index on products.sku

The database was updated through Supabase MCP and the SQL migration was recorded for future deployments.
```

## Core Rule

**Every persistent Supabase database change made through MCP MUST be reproducible from a migration file committed to the repository.**

Never treat a direct MCP database change as a substitute for a migration.
